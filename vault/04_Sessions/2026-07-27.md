## Partial-image labeling discussion

The user described the existing workflow: 100-300 images per orbit, reviewed
as 6x6 overview figures, with usually zero or one manually selected good
sequence. Approximately 400,000 source images and 11,098 overview figures make
per-image pixel masks infeasible.

Visual inspection of orbit 169 shows a useful auroral region coexisting with a
bad lower-edge region that grows gradually over consecutive frames. The
recommended annotation unit is therefore an orbit interval plus sparse mask
keyframes. One drawn boundary/polygon applies forward until changed; two or
three keyframes can be interpolated through a partial interval. Exceptional
geometries can remain discarded.

The inspection also found a label-integrity issue. Orbit 169 is recorded as
good from 0 through 51 in `good_orbit_segments_old.csv`, but the current CSV
replaces the zero start with a blank. Older scripts treat a blank start as
zero; `scripts/IMAGE/helpers.py` skips blank starts. Many zero values differ
between the two CSVs, so label-state semantics must be repaired before a new
annotation campaign.

## First annotation trial follow-up

The user's first desktop trial revealed that `usable start` was easy to
misread as the start of a new partial interval. In the schema it is instead
the first usable frame of the entire envelope, so setting it after orbit 169's
fully good start at frame zero correctly failed but did not explain the
intended workflow.

The four controls were renamed to FIRST/LAST usable and FIRST/LAST fully good.
The interface now explains that a later partial section is created by selecting
its final useful frame and changing only LAST usable. A targeted diagnostic is
shown if FIRST usable is selected after an existing fully good start. A
headless regression reproduced the user's action and verified that FIRST
usable remains zero, LAST usable can become 72, and frames 52 through 72 are
then classified as partial. A second desktop trial is still required.

## Mask-editor and propagation follow-up

The second desktop trial successfully extended orbit 169's usable envelope to
frame 233, but neither double-click nor the edit button appeared to open a
mask editor. The cause was an overly broad backend check: it skipped
`figure.show()` for any backend name containing `agg`, which unintentionally
included GUI backends such as Qt5Agg and TkAgg.

The editor now skips explicit display only for exact non-GUI Agg, brings Qt/Tk
windows to the foreground, and catches construction errors so they appear in
the main status panel. A headless callback regression confirms that editing
frame 52 creates and retains a mask-editor object.

The user rejected temporal mask interpolation. Propagation now uses
forward-held step semantics: a keyframe mask applies from its own frame until
the next keyframe. Each partial interval must start with an exact keyframe, so
orbit 169 requires its initial partial mask at frame 52. Tests verified that a
mask at 52 remains unchanged through 99, a replacement at 100 applies from
100 through 233, and completion rejects an initial keyframe placed only at
frame 60. Repository-wide AST parsing still succeeds for all 43 Python files.
